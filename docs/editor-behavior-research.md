# Editor behavior research and acceptance baseline

Checked **2026-10-28** against primary documentation and Span source at [`39bb73c`](https://github.com/1kentom/span/commit/39bb73c2696b10543fe680fccd4a0aabf6f8e07d). This is a documentation audit of existing implementation and a baseline for subsequent changes. It does not establish that this research preceded the existing code. Before the next feature change, refresh the relevant row and define its acceptance checks before implementation, as required by [the execution checklist](implementation-goal.md).

“Documented” below means observed in the linked documentation or source, not independently exercised in another editor. Rolling documentation was checked on the date above; its behavior may differ from older releases. Test links identify existing coverage, not a new test run or a native verification claim.

Fleet is a **historical reference**. JetBrains [ended downloads on December 22, 2025 and stopped further updates](https://blog.jetbrains.com/fleet/2025/12/the-future-of-fleet/); that announcement now also describes its successor, Air. Several Fleet help URLs redirect to this notice. Surviving Fleet 1.48 help and dated release notes below do not establish current Air behavior. Missing Fleet details remain unknown rather than borrowing IntelliJ behavior.

## Review limits and remaining gates

The protocol's [permission-option semantics](https://agentclientprotocol.com/protocol/v1/tool-calls#permission-options) assign remembered-decision scope and lifetime to the agent. Span's existing client cache is session-scoped, but this does not prove that a selected provider's `allow_always` decision cannot persist longer. Verify the real adapter's option names, actual policy, authentication and proposal handling under #13 before describing its behavior as guaranteed.

The ACP references are the site's **v1** documentation as served on 2026-10-28, separately from its v2 draft. They describe the protocol contract, not verified conformance of every installed adapter or SDK release.

| Open issue, checked 2026-10-28 | Evidence boundary and acceptance still needed |
| --- | --- |
| [#12 Native performance](https://github.com/1kentom/span/issues/12) | Measure native startup, typing and large-file budgets using reproducible methods. Browser responsiveness, screenshots and packaging do not establish those budgets. |
| [#13 Real provider proposal](https://github.com/1kentom/span/issues/13) | Authenticate a supported real provider; generate an actual proposal; verify native review, acceptance, rejection and failure handling. Fake subprocess fixtures and a successful prompt are insufficient. |
| [#20 Settings/keybinding compatibility](https://github.com/1kentom/span/issues/20) | Validate and document the supported subset and conflicts; never equate familiar names or table columns with complete VS Code compatibility. |
| [#21 Split/drag lifecycle](https://github.com/1kentom/span/issues/21) | Chromium internal drag tests do not verify Windows WebView2: its native external-drop handler conflicts with HTML5 internal dragging. Choose and verify a platform strategy before claiming that workflow. |
| [#29 Markdown Run](https://github.com/1kentom/span/issues/29) | Copy/render callbacks do not establish execution. Wire Run to real PTY output and verify error, cancellation and cleanup in the installed app. |
| [#30 Background indexing](https://github.com/1kentom/span/issues/30) | Current opening waits for scanning; safe transition locking does not make indexing incremental. Implement cancellable background work, stale-result guards and measured early usable state. |
| [#31 Dirty content / clean-tab LRU](https://github.com/1kentom/span/issues/31) | Content-based dirty correction has regression coverage. The configurable default-10 clean-only eviction policy still needs implementation and verification across history and split views. |

This research pass changed documentation only and ran no application, live provider or performance benchmark. Exact test-run, hosted CI, installed-build and publication results belong in [the execution checklist](implementation-goal.md) and [release records](releases.md), with the tested commit identified. Reuse the linked tests as acceptance checks, then add a failing reproduction for any newly found defect rather than inferring readiness from this comparison.
