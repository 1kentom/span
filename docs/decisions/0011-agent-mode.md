# 0011: Agent mode

Status: accepted by the owner on 2026-10-29, who delegated the individual
decisions below and approved them as recorded. Planning only: no code ships
with this record. Builds on 0001 (session manager), 0003 (span-agents tool
server), 0005 (session metadata, amended by this record), 0009 (warm start)
and 0010 (health check). Tracking issue: #146.

## Context

Span's agent work lives in the editor's agent sidebar. One controller,
`ui/src/lib/agent-controller.ts` (about 2,460 lines), owns the connection,
the open chat, its feed, handoff, review and metadata writes. The backend
already holds several connections and sessions (0001, `SessionKey {
connectionId, sessionId }`), delegated children (0003), warm background
agents (0009) and hidden health sessions (0010), but the UI shows one chat at
a time and the per-session wrapper event of 0001 section 3 is still not
exported to TypeScript.

The owner wants an "agent mode": a full page for running and reviewing many
agent threads at once, in the spirit of the supplied local design archive
(a sessions rail, a central thread, and a side panel with changes, agents and
files). The archive stays local and out of Git (AGENTS.md); this record
describes it only in words and copies nothing from it.

Constraints carried over:

- Layering from AGENTS.md: business logic in `crates/core`, ACP in
  `crates/acp`, Tauri glue in `apps/desktop`, frontend in `ui`. IPC types
  are generated by specta and tauri-specta, never duplicated by hand.
- From 0003: answers to permissions, elicitations and edit reviews are
  user only and never reachable from an agent; delegated work never
  outlives its lead; settings that change what agents may do are honoured
  only from the user's own settings file; no new direct dependencies
  without the owner's approval.
- Public documents stay specific about what was verified in the browser
  preview, in tests, and in the native app.

### Research findings

Read from the products' public sources and issue trackers, not from runs of
those products (UNVERIFIED section).

- T3 Code: providers sit behind adapters that declare capability flags, and
  the UI asks the flags instead of branching on the provider. Checkpoints
  are commits on hidden git refs outside the user's branches, and a restore
  rolls back all files of a checkpoint or none. Streaming text is buffered
  and flushed on a short interval rather than rendered per token.
- Zed: ACP threads do not keep history across restarts the way its native
  agent does, and they lose the native thread's review surface. Its
  checkpoint restore has no undo: restoring discards later work with no way
  back.
- Across these tools, the most common serious bug class is permission
  leaks: an approval mode or an "always allow" escaping its intended
  scope, set by something other than the user, or bypassed by a code path
  the policy did not cover.

## Decisions

### a. Transcripts may be stored locally

ADR 0005 kept prompt text and replies off disk. Agent mode needs a thread to
reopen with its content even when the agent cannot replay it, so this is
relaxed under these rules:

- Location: the app data folder only, beside the session metadata
  (`<home>/.config/span/`, a `transcripts/` folder keyed by the same
  `workspace_hash`). Never inside the workspace or `.span`.
- One file per thread, so clearing or evicting one thread touches one file.
- Size caps per thread and in total. Over the per-thread cap the oldest
  items are dropped first; over the total cap whole threads are evicted,
  least recently active first, archived last (the 0005 eviction order).
  The exact numbers are set in phase 1 and recorded here by amendment.
- Before every write, secrets are scrubbed with the same rules as
  `redact_log` in `crates/acp/src/service.rs` (authentication metadata,
  `_auth/*` params, MCP server header and environment values), factored so
  the log and the transcript writer share one implementation. The
  span-agents bearer token never reaches disk.
- Setting `agents.transcripts.store`, default on, honoured only from the
  user's own settings file. It joins the user-only keys in
  `crates/core/src/settings.rs` (`agents.delegation.enabled`,
  `agents.runTools.enabled`, `agents.warmStart`, `agents.healthCheck`,
  `agents.startMode`, `updates.checkOnLaunch`) with the same treatment:
  dropped from workspace settings before merging and never written to a
  workspace file. This record only describes the key; the Rust change is
  phase 1 work.
- A "Clear history" control removes all stored transcripts for the folder
  (and one thread's transcript from that thread's menu). Turning the
  setting off stops new writes; it does not silently delete what exists.
- Replay wins: when the agent advertises `session/load`, the thread is
  restored from the agent and the stored transcript is only a fallback
  (agents without load, or a load that fails). Span never shows both.
- ADR 0005 is amended accordingly (its Amendment section).

### b. Agents mode replaces the editor area

- A full page that takes the editor area: a sessions rail (threads of the
  folder, with state), the thread in the centre, and a side panel with
  Changes, Agents and Files tabs.
- Switched by an Editor/Agents control and Cmd+Shift+A (Ctrl+Shift+A on
  Windows and Linux; the chord is unbound in `ui/src/lib/commands.ts` at
  the time of writing).
- Editor mode keeps the agent sidebar as it is today.
- Both views read one session store, so a thread is the same thread in
  both: same feed, same running state, same pending requests. Switching
  view never starts, stops or reloads a session.

### c. Worktree per thread is deferred

Threads share the open folder until phase 6. Two threads editing the same
files can conflict; the Changes tab shows which thread proposed what, and
the user is expected to avoid running overlapping writers until then.

### d. Permissions

- The default for every thread is ask: Span's approval prompts appear.
- Modes are per thread, not global, and are enforced at the adapter
  (`crates/acp/src/adapter/`), so a UI bug cannot widen them.
- No mode may be set by an agent (no tool, MCP method or ACP request path
  changes it) or by workspace settings (the 0003 section 6 rule; this
  extends the existing user-only `agents.startMode`).
- Every mode and every path that answers a request is covered by tests
  (the permission matrix of phase 5), following the 0001 section 6 and
  0003 section 4 tests that drive every agent-reachable path while a
  request is pending.

### e. Verification policy

- Claude agents working on Span cannot see the native window. They verify
  with unit, component, process and browser preview tests and say so.
- The owner does a visual pass in the native app at each phase gate,
  from `docs/agent-mode-checklist.md`.
- Nothing is called native-verified without evidence (the owner's pass
  recorded on the issue or PR, or a captured artifact).

### f. Phases

Each phase is its own PR or PR series, gated on its tests and, where it
changes what the user sees, the owner's checklist pass.

0. Ground truth: this record, the amendments to 0001, 0003 and 0005, the
   checklist, and the tracking issue. No code.
1. Backend multi-session: commands and events keyed by `SessionKey`
   (connection id plus session id) instead of "the active agent", the
   0001 wrapper event registered with tauri-specta so the bindings carry
   it, the transcript store in `crates/core` with its user-only setting,
   caps and scrubbing.
2. Frontend stores: split `agent-controller.ts` into app-wide stores
   (connections, installed agents, health, session states, metadata) and a
   per-thread store (feed, composer, review, handoff), one instance per
   open thread. The sidebar keeps working on top of them.
3. Page shell: the Agents page (rail, thread, side panel tabs), the
   Editor/Agents control and Cmd+Shift+A, sharing the stores of phase 2.
4. Review: Span's own diff tracking per thread (not only ACP proposals),
   per-hunk accept and reject, and follow-agent (the editor or Files tab
   follows the file the agent is editing, can be turned off).
5. Safety: checkpoints in hidden git refs (outside branches and the user's
   index) with a snapshot taken before every restore so a restore can be
   undone; restore is all-or-nothing. Plan mode enforced at the adapter
   (no writes, no command execution). The permission matrix tests of d.
6. Scale: worktree per thread; a steer vs queue choice for a prompt sent
   while a turn runs (0001 section 4 already refuses with
   `PromptError::Busy`); goals and budgets per thread (extending 0003
   section 4 budgets); the child-session tree in the rail.
7. Verification: recorded-transcript replay tests in CI (real agent
   transcripts, scrubbed, replayed through fixture agents), the owner's
   native passes for every phase, and an accessibility pass (keyboard
   only, focus order, screen reader names, reduced motion).

From the research: adapters declare capability flags (load, close,
delete, modes, plan, http MCP) and the UI reads flags, not agent names;
checkpoints follow the hidden-ref, all-or-nothing model but add the undo
snapshot Zed lacks; streaming text is buffered per thread so many busy
threads do not flood the webview; history and review must work for ACP
threads, which is the gap seen in Zed.

## Consequences

- Prompt text, replies and tool output can now exist on disk in the app
  data folder, scrubbed and capped, under a user-only switch. Users who
  turn it off keep 0005's behaviour.
- The 0001 promise that `AgentEvent` stays unchanged holds: the new events
  are the keyed wrapper, not new fields on every variant.
- `agent-controller.ts` stops being the single owner of agent state; tests
  that drive it move to the stores in phase 2.
- Until phase 6, several threads write into one folder.
- Each phase adds owner time for the checklist pass.

## Known risks

- Permission leaks: a per-thread mode applied to the wrong session (the
  same session id on two connections, 0001 section 2), a delegated child
  inheriting a looser mode than ask, or a new answering path added for the
  page that bypasses the user-only rule. Mitigated by keying everything by
  `SessionKey`, enforcing at the adapter, and the phase 5 matrix.
- Transcripts on disk: a secret the scrubber does not know about (an API
  key pasted into a prompt, a token printed by a tool) is stored as text.
  Scrubbing covers protocol secrets only. The setting and Clear history are
  the user's controls; this is stated in the UI.
- Replay vs stored copy divergence: an agent's `session/load` can differ
  from what Span stored. Replay wins, so the stored copy is never merged.
- Many live threads: event volume and memory in the webview, and agent
  processes per folder on top of 0009's four warm agents.
- Restore without undo destroys work (the Zed case). Phase 5 must take the
  snapshot before touching files, and a failed restore must leave files as
  they were.
- The controller split is large and touches the most tested UI file;
  regressions in the sidebar are likely without the phase 2 tests.
- Shared folder before phase 6: two threads can overwrite each other.

## Amendment: phase 1 keyed API (2026-10-29)

The first phase 1 PR adds the keyed backend; the transcript store is a
later PR.

- Events: `AgentKeyedEvent` carries every event of every connection with
  its `SessionKey` (0001 section 3 update). Span-agents events are sent on
  it too, keyed by their lead.
- Commands by key: `agent_open_session` (a new lead on a given connection,
  on a process for a command, or on the focused connection; returns the key
  and never closes another session), `agent_live_sessions` (key, parent
  key, origin, depth, state, queued count, agent name and installed id,
  title, model, mode, health), `agent_focused_session`, and the `_keyed`
  forms of prompt, cancel, permission, elicitation, set config, review,
  review hunks and close.
- The desktop holds a focused session (the sidebar's chat) beside the
  sessions of the manager. The unkeyed commands resolve to it, so the
  sidebar behaves as before. `agent_connect` still replaces the focused
  agent, but a connection that holds a lead opened by key is kept alive
  instead of closed, and stops feeding the old sidebar channel.
- Rules kept: answers go through `SessionManager` and are checked against
  the full key (permission and elicitation alike); closing a lead cascades
  to its children; each lead gets its own span-agents server and token.
- Not in this PR: focusing a session on another connection (refused), sign
  in for a connection opened by key (the open fails instead), ending a
  process started by key when its last session closes (it ends with the
  folder), and the transcript store.
